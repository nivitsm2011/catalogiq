Every pinned package (torch, faiss-cpu, chromadb, opencv) ships x64 wheels; ARM64 wheels are missing for several. Project requires 3.11. Cost: slower CPU via emulation. |
| 2026-10-03 | CPU-only torch build | CUDA build | No NVIDIA GPU; code auto-uses a GPU if present (`utils.get_device`). |
| 2026-10-03 | `tasks.ps1` as primary task runner, Makefile kept for macOS/Linux | Make on Windows | `make` is not installed on this machine; PowerShell script needs no extra tooling. |
| 2026-10-03 | Pin top-level packages to the versions resolved at setup time (`requirements.txt`) | Pin full transitive lock | Keeps the file readable; transitive versions are resolved by the pinned top-level ones. |
| 2026-10-03 | ruff + black line length 100 | Default 88 | Fewer awkward wraps in long config/path code. |
| 2026-10-04 | Parse `styles.csv` by splitting each line on the first 9 commas (`maxsplit`) instead of `pd.read_csv` | `read_csv(on_bad_lines="skip")`; quoting heuristics | `productDisplayName` is the last column, so extra commas always belong to it. Result: 22 rows repaired, 0 lost, 0 unrecoverable. Silently skipping would have dropped real products. |
| 2026-10-04 | Drop the 5 products whose image file is missing (44,446 -> 44,441); no corrupt or tiny images were found | Keep rows, impute | A product without a readable image cannot be trained on, shown to a shopper or checked by the quality checker. |
| 2026-10-04 | Near-duplicate photos = pHash Hamming distance <= 1 (1,553 groups, 3,932 images, largest group 30) | Threshold 2 (chosen first); exact-hash only | At distance 2 the clusters chain: side-view shoes of different products merged into one 2,859-image component, which made a 70/15/15 split impossible (got 65.6/14.1/20.3). Distances 0 and 1 give identical groups, so 1 adds tolerance with no chaining. |
| 2026-10-04 | Split by near-duplicate group, stratified by articleType (20 folds -> 14/3/3 = 70/15/15), seed 42 | Plain stratified random split | The same photo (or a re-shot copy) in train and test lets the model memorise the answer and inflates test accuracy. The group-aware split gives exactly 70.0/15.0/15.0 (29,579 / 6,339 / 6,339 rows) and 0 groups spanning splits (checked in the pipeline and by a unit test). |
| 2026-10-04 | articleType: drop classes with < 100 images (143 -> 55 classes; with the rare masterCategory drops, 2,184 rows = 4.9% of 44,441 in total) | Merge into "Other"; keep all | A seller-facing tool cannot promise a product type it has seen fewer than 100 times, and an "Other" bucket mixing dozens of unrelated types teaches the model nothing. Those rows are excluded from training; at inference a low-confidence prediction is shown as "unsure, please choose". |
| 2026-10-04 | Rare-class pass for drop-policy targets repeats until stable; merge-policy targets run last | Single pass in column order | After dropping rare articleTypes, one masterCategory fell to 12 images (a 1,724x imbalance). The repeated pass drops it (12 more rows, final 42,257) so the final table satisfies every threshold. Covered by a regression test. |
| 2026-10-04 | masterCategory: drop < 50; gender: drop < 100 (none affected); subCategory, baseColour, season, usage: merge < 100 into "Other" | Drop everywhere | For attributes that sellers fill in as a form field, "Other" is a legitimate answer; for the core taxonomy a vague bucket would be wrong rather than unhelpful. Merged: subCategory 3 classes / 108 rows, baseColour 1 / 56, usage 3 / 112. |
| 2026-10-04 | Collapse 47 raw colours to a 15-colour retail palette (`configs/colour_map.yaml`); `Metallic` and `NA` go to "Other" | Keep 47 shades; fewer than 15 families | Shoppers filter by colour family ("Blue" should include Navy and Turquoise) and sellers pick from a short list. 47 shades with tiny classes would be unlearnable, and 44% of look-alike photo groups already disagree on colour. The raw colour is kept in `baseColour_raw`. |
| 2026-10-04 | Keep all 7 targets for now; publish a target only if it beats its majority-class baseline on the test set in Phase 2. Season and usage are provisional | Drop season/usage now | Evidence (`reports/target_evidence.csv`): look-alike photos disagree on season 18.1%, usage 9.9%, articleType 12.0%, gender 7.9%, subCategory 3.8%, masterCategory 0.5% and colour 44.0% (partly legitimate colourways). Usage is 77.7% "Casual", so the bar is high. A real photo model is the proper test, so the final call is made on measured lift, not on this proxy. |
| 2026-10-04 | Stream Amazon_Fashion via `datasets` (text builder, JSON lines parsed ourselves) in 3 passes: count reviews per item, fetch metadata for the top 1,600 candidates, fetch reviews of the final 800 items | `load_dataset("json")` (Arrow schema inference); downloading the dump | Amazon metadata has mixed-type fields (`price`, `details`) that break Arrow schema inference. Nothing is stored except the sample: 800 items, 139,400 reviews, 17.5 MB (cap 300 MB). |
| 2026-10-04 | Review cleaning: strip HTML, drop reviews < 30 chars, drop same-text duplicates per item, cap 300 reviews per item (seeded reservoir sample) | Keep everything; keep newest | Very short reviews ("ok", "nice") carry no evidence for Q&A citations; duplicate texts are copy-paste or bot reviews; a per-item cap stops a few huge items dominating retrieval. |
| 2026-10-04 | Listing quality score = Bayesian-shrunk rating rescaled to 0-1: `shrunk = v/(v+50)*R + 50/(v+50)*C`, `score = (shrunk-1)/4`. Exemplar = score >= 0.85, >= 50 ratings, title >= 20 chars, >= 3 bullets | Raw average rating; rating x log(volume) | A 5.0 with 3 ratings should not outrank a 4.6 with 2,000, and shrinkage expresses "high rating x enough ratings" in one explainable number. A first threshold of 0.80 gave 47.5% exemplars (too lenient); 0.85 gives 191 of 800 (23.9%). |
| 2026-10-04 | EDA compares "performing" listings using score and volume only, not completeness | Compare exemplars | Exemplars require >= 3 bullets by definition, so comparing bullet counts would be circular. |
| 2026-10-06 | Network input 128x96 (height x width) instead of 224x224; images cached once as uint8 at 80x60 | 224x224; 160x120 | Source photos are about 60x80 px, so 224 only adds interpolation, not information, and cost about 3x the compute (benchmark: 28.6 vs 201.7 img/s fine-tune step at 224x168 vs 128x96). Aspect ratio 4:3 preserved. Later re-measurement gave about 98 img/s for fine-tuning at any batch size, so the earlier benchmark was optimistic; time estimates use the re-measured figure. |
| 2026-10-06 | MobileNetV3-Large backbone for the multi-output model | EfficientNet-B0; ResNet-50 | About 5.4M parameters and 22 MB of weights, a 13 MB exported model, built for CPU/mobile; 18.7 ms per image inference measured. EfficientNet-B0 was NOT benchmarked here, so the choice rests on published size/FLOPs and measured MobileNet speed, not on a head-to-head test. |
| 2026-10-06 | Class-weighted loss with weight ~ (1/count)^0.5 instead of oversampling | Oversampling rare classes; full inverse-frequency weights | Our data has near-duplicate photos, so duplicating rare-class images encourages memorising them; oversampling also lengthens every CPU epoch. Square-root weights are a gentle middle that does not let a handful of rare photos dominate the loss. |
| 2026-10-06 | Augmentation: flip, rotation +-10 deg, scale, translation, brightness/contrast/saturation; hue shift forced to 0 (the code raises if set) | Standard colour jitter with hue | A hue shift changes a navy shirt into purple and would corrupt the baseColour label. Covered by a unit test on a pure-blue image. |
| 2026-10-06 | Batch-level augmentation in torch on cached uint8 arrays, no DataLoader workers | torchvision transforms with workers | Avoids JPEG decoding and Windows multiprocessing overhead; the data path costs about 65 ms per 128-image batch against about 1.3 s for the model step. |
| 2026-10-06 | MLflow local file store enabled via `MLFLOW_ALLOW_FILE_STORE=true` | SQLite store (`sqlite:///mlruns/mlflow.db`) | The project brief asks for a local file store; MLflow 3.16 refuses it by default and marks it as maintenance-mode. SQLite is the supported alternative and is a one-line change in `tracking.py` if the file backend is removed. |
| 2026-10-06 | Pretrained weights cached inside the project (`models/cache`, via `TORCH_HOME`/`HF_HOME`) | Default user-profile caches | Brief requires everything in one folder and a footprint under about 5 GB. MobileNetV3 weights 22 MB; CLIP ViT-B/32 laion2b 605 MB (approved before download). |
| 2026-10-06 | Baselines: majority class, frozen MobileNetV3 embeddings + logistic regression (C=1.0), zero-shot CLIP ViT-B/32 with one prompt template per target (test split only) | Prompt tuning for CLIP; stronger classifiers | Simple, explainable numbers to beat. CLIP templates were written once and not tuned on the test set. |
| 2026-10-06 | Reduced training run: 4 heads-only + 6 fine-tune epochs (planned 6 + 10) | Full planned run (about 80 min); 50% data subset | Measured about 3.2 min and 5 min per epoch on CPU; the project owner chose the reduced run. Validation macro-F1 was still flattening (0.7713 at fine-tune epoch 5, 0.7708 at epoch 6). |
